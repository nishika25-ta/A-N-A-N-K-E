# ANANKE policy specification, v0 (draft)

**Schema versions:** `ananke.policy/0`, `ananke.action/0`, `ananke.scenario/0` · **Status:** sections 1 to 10
are **implemented and tested** (Phases 0 to 4).
Where this document and the code disagree, that is a bug.
All semantics are **default deny** and **fail closed**.

## 1. Identifiers

- `principal_id`, `rule_id`, `tool_id`, `operation`, `session_id`, `actor_id`: lowercase ASCII identifiers matching
  `[a-z][a-z0-9]*([-_][a-z0-9]+)*`, at most 128 characters (`ananke.domain.identifiers.validate_identifier`).
- IDs are **never reused**. A regrant always gets a new `rule_id`.
- Event, request and approval IDs are UUIDs, generated by trusted code (never taken from model output).

## 2. Resources

- MVP resources are synthetic: `<namespace>:<name>`, e.g. `ticket:demo-42`
  (`validate_resource`). They are never filesystem paths.
- Rejected outright, not normalized: non-ASCII (including homoglyphs), `..`, `/`, `\`, `*`, `?`, `%`,
  whitespace, empty segments, an extra `:`, uppercase namespace, a leading or trailing delimiter, or length over 128.
- **Matching is exact string equality** on validated resources. Prefix or wildcard scopes are **not supported**
  in v0 (see ADR-0001). If added later, they must be explicit, delimiter-aware and property-tested.

## 3. Policy events (operator channel only)

| Field | Type | Notes |
|---|---|---|
| `event_id` | UUID | |
| `sequence` | int ≥ 1 | Contiguous, assigned by the ledger |
| `epoch` | int ≥ 1 | Epoch *after* applying this event |
| `kind` | `GRANT` \| `DENY` \| `REVOKE` \| `SUPERSEDE` | |
| `actor_id` | identifier | Must be a registered operator (`operators` table), assigned by the channel |
| `recorded_at` | int tick | Clock reading at recording. Non-decreasing along the chain |
| `rule_id` | identifier | New rule created (GRANT, DENY, SUPERSEDE) |
| `target_rule_id` | identifier \| null | Required for REVOKE and SUPERSEDE, forbidden otherwise |
| `principal_id`, `tool_id`, `operation`, `resource_scope` | identifiers / resource | Required for GRANT, DENY, SUPERSEDE |
| `valid_from` | int tick ≥ 0 | |
| `valid_until` | int tick \| null | `null` = no expiry. Must be `> valid_from` when set |
| `requires_approval` | bool | GRANT and SUPERSEDE only (`false` for DENY) |
| `reason` | short string | Operator note; never shown to the model unredacted |
| `prev_hash`, `event_hash` | `sha256:<hex>` | Hash chain, section 6 |
| `schema_version` | `"ananke.policy/0"` | Unknown versions are rejected |

**Transition rules** (an invalid event is *rejected*, never reinterpreted):

- `GRANT` / `DENY`: `rule_id` must be unused. Creates an active rule.
- `REVOKE`: `target_rule_id` must name a currently **active** rule (not revoked or superseded). The rule
  becomes `revoked`. Revoking an *expired* but still active rule is allowed and recorded.
- `SUPERSEDE`: `target_rule_id` must name an active rule with the same `principal_id` **and
  `tool_id`**. The replacement **inherits the target's effect** (GRANT or DENY). A superseded DENY may
  not become a rule that requires approval. In one event, it retires the target (status `SUPERSEDED`,
  `replaced_by` set) and creates the replacement `rule_id`. Use it for scope changes such as narrowing the
  operation or resource.
- Each accepted event increments `epoch` by exactly 1. **Expiry does not change the epoch.** Expiry is
  evaluated against the clock at decision time.
- Unknown fields, unknown kinds, a non-contiguous `sequence`, an unexpected `epoch`, a broken `prev_hash`,
  a recomputed `event_hash` mismatch, and `recorded_at` regression are all rejected
  (`TransitionError` codes). Batches submitted together are atomic: all are committed or none are.

The **reducer** is a pure function `events → {rule_id → Rule(status, fields)}`. Replaying the same events
must always produce the same state (property-tested in Phase 1). A snapshot (`epoch`, active rules,
`snapshot_digest`, `as_of_tick`, `last_event_hash`) is a cache. **It never authorizes an effect on its own.**

## 4. Decision algorithm (reference monitor)

Inputs: an `ActionRequest` built by `AgentPort` (identity bound by the port, never by the proposal), the
latest committed ledger state, and the clock `now`. Everything below happens in **one**
`BEGIN IMMEDIATE` transaction (ADR-0002). The first step that fails decides the outcome:

1. Verified policy state (`PolicyReader`): a broken chain or invalid replay gives `POLICY_INVALID`. A lock or I/O failure
   gives `LEDGER_UNAVAILABLE`.
2. An unregistered `tool_id` gives `UNKNOWN_TOOL`. An unknown operation for the tool, a resource outside the tool's
   namespace, or arguments failing the operation's strict schema give `INVALID_ARGUMENTS`.
3. Idempotency (section 7): the same key with the same action digest gives `ALLOW` + `DUPLICATE_REQUEST`
   with `duplicate_of` set, **no new effect and no content**. The same key with a different digest gives
   `DENY` + `IDEMPOTENCY_CONFLICT`.
4. **Applicable** rules: `status == ACTIVE` ∧ same principal, tool, operation ∧ exact resource ∧
   `valid_from <= now < valid_until` (or `valid_until` null).
5. Any applicable **DENY** gives `EXPLICIT_DENY`. *Deny wins.*
6. With no applicable GRANT, the diagnostic is chosen deterministically, in this precedence, from ledger facts
   only:
   - a matching grant exists with status `REVOKED` or `SUPERSEDED`: `GRANT_REVOKED`;
   - else a matching active grant exists with `now >= valid_until`: `GRANT_EXPIRED`;
   - else `NO_MATCHING_GRANT` (this includes not-yet-valid grants).
   `matched_rule_ids` lists the rules behind the diagnostic. A rule is never fabricated.
7. If **any** applicable grant has `requires_approval` (conservative union), approval is required
   (section 5). With no `approval_id`, the result is `NEEDS_APPROVAL` + `APPROVAL_REQUIRED`.
8. Otherwise the request is allowed: the effect handler runs, a `lab_effects` row is written, the approval is consumed, and
   the decision and idempotency rows are appended. Then `COMMIT`.

Any exception in steps 1 to 8 rolls back the whole transaction. A DENY is then recorded in a new
transaction: `POLICY_INVALID`, `LEDGER_UNAVAILABLE`, `INVALID_ARGUMENTS` (a post-authorization tool error,
e.g. a missing record for a write), or **`INTERNAL_ERROR`** (an extension code). If that record cannot be
written either, the gateway raises `GatewayUnavailableError` (the run must stop).

A proposal that cannot be parsed at all (unknown or identity fields, floats, bad identifiers) is
recorded as `DENY` + `INVALID_ARGUMENTS` with no action fields. `observed_epoch` is informational only.
A receipt carries `result` only for an **allowed read**, and carries no internal hashes besides `action_digest`.

## 5. Approvals

An approval is issued by `OperatorChannel.issue_approval(action: ActionCore, expires_at)`. The operator
approves the **exact action**, and the channel computes `action_digest` itself. A digest supplied by agent code
is never accepted. The approval records `issued_epoch` = the current epoch and `issued_at` = now, and
requires `expires_at > now`. Validation happens inside the gateway transaction:

- unknown `approval_id`, or a different principal, session or action digest: **`APPROVAL_INVALID`** (an extension
  code);
- already consumed: `APPROVAL_REPLAY`;
- `issued_epoch != current epoch` (**any** accepted policy event invalidates it) or
  `now >= expires_at`: `APPROVAL_STALE`.

Consumption (`consumed_at`, `consumed_by` = decision id) happens in the same transaction as the effect.
A database trigger allows only one transition from unconsumed to consumed, and forbids every other
update or delete. An approval presented for an action that no longer needs one is ignored and not consumed.

## 6. Canonicalization and hashing (`ananke-cjson-1`, implemented in Phase 0)

- Types: object (string keys), array, string, integer, boolean, null. **Floats, NaN and Infinity are rejected.**
  Integers satisfy `|n| ≤ 2^53−1`. Strings must already be NFC and valid UTF-8 (they are rejected, not normalized).
  Maximum nesting depth is 32.
- Bytes: UTF-8, keys sorted by code point, separators `,` and `:` with no whitespace, non-ASCII emitted literally.
- `digest = "sha256:" + hex(SHA-256(canonical bytes))`.
- `event_hash = digest(event without event_hash)`. Genesis `prev_hash = "sha256:" + "0"*64`.
- `action_digest = digest({schema_version, principal_id, session_id, tool_id, operation,
  canonical_resource, arguments})`.
- Test vector, the masterplan example event:
  `sha256:f45d73cad23965b1fffed61db1db099b4f80139d16c9ced3e04831fb655260d8`.
- A digest is integrity evidence. It is not a signature, not authentication and not proof that the content is true.

## 7. Idempotency

Keys (`[A-Za-z0-9][A-Za-z0-9_-]{0,63}`) are scoped to `(session_id, principal_id)`. **Only committed
effects bind a key.** A denied or needs-approval request does not, so the agent may retry with the same
key after the policy changes or an approval is issued. A bound key returns the stored decision reference
without a new effect and without content, whatever the current policy. This is safe because the effect
already committed under valid policy at its own linearization point. Concurrent duplicates are
serialized by the write lock, and exactly one effect commits (tested with 4 threads).

## 8. Provenance labels (implemented: `ananke.memory.entries`)

`MemoryEntry.trust ∈ {UNTRUSTED < TOOL_OUTPUT < OPERATOR}`, `sensitivity ∈ {PUBLIC < INTERNAL < RESTRICTED}`.
Trust is fixed by the **origin channel**, never by content: TASK and OPERATOR_NOTICE give OPERATOR, TOOL_RESULT gives
TOOL_OUTPUT, AGENT and SUMMARY give UNTRUSTED. A derived entry gets `trust = min(sources)`, `sensitivity = max(sources)`,
`source_ids` = the resolvable sources, and `resource_refs` = their union. **Any** unresolvable claimed source makes it
`UNTRUSTED` + `RESTRICTED`. Property-tested: summaries never promote labels and never invent lines.

## 9. Model-visible policy grammar and projection (implemented; ADR-0011)

One fact per line, a fixed field order:

```
POLICY SNAPSHOT epoch=<e> principal=<p|*> now=<t> complete=<yes|no>
POLICY GRANT <rule> <tool>.<op> <resource> principal=<p> from=<t> until=<t|none> approval=<yes|no> epoch=<e>
POLICY DENY  <rule> <tool>.<op> <resource> principal=<p> from=<t> until=<t|none> approval=no epoch=<e>
POLICY REVOKE <rule> epoch=<e>
POLICY SUPERSEDE <rule> epoch=<e>
```

Resolution rules for a reader: per rule, the latest epoch wins. A `complete=yes` snapshot at epoch S retires every rule
for that principal (or for every principal with `*`) whose latest statement has epoch ≤ S and that is not listed in the
snapshot block. **The projection (M5)** is a complete snapshot for one principal and its enabled tools, plus REVOKE or SUPERSEDE
warnings for rules this session was shown. **Full policy (M4)** is a complete snapshot of every active rule for every principal.
Both are rendered deterministically from the reduced ledger. The assembler raises `BUDGET_EXCEEDED` rather than truncate
them. Sections whose header is `UNTRUSTED DATA` hold quoted non-operator content and are never policy. **The gateway
always evaluates the full ledger, whatever any context says.**

## 10a. Signatures and checkpoints (implemented; ADR-0010)

A ledger is **signed** when created with a public key for every operator (`ledger_config.signing = required`). Then:
every policy event and approval carries an Ed25519 signature over `ananke-sig-1\n<kind>\n<record_hash>` by its
issuing operator's registered key. The reader, verification and the gateway's approval check reject a missing, invalid or
mis-attributed signature (fail closed). A **checkpoint** is a signed record of the three chain heads, stored outside the
database. `verify_checkpoint` reports truncation and rewrites below it. Unsigned ledgers are reported as
`authenticity: unsigned`.

## 10. Evidence audit (implemented: `ananke.audit`)

`ananke ledger verify` checks the structure of the policy, approval and decision chains. Then it **replays every
policy-derived decision** with the evaluator against the ledger state at that decision's epoch and tick, and cross-checks
`lab_effects`, `approval_consumptions` and `idempotency` against the ALLOW decisions that justify them, in both directions.
Exit 0 only if both pass. On unsigned ledgers, forgery that stays consistent under a registered operator identity still
passes. Signed ledgers (section 10a) close that gap.
